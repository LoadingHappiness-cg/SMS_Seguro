# OTA Refresh Release 0.1.5 Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Ship a new APK release so the manual OTA update action always triggers a fresh ruleset fetch and the UI can move past stale `v5` state.

**Architecture:** Keep the change minimal. Update the WorkManager policy for manual checks so stale one-time work cannot block a new OTA request, then bump the app version for a new signed release. Reuse the existing ruleset metadata UI and OTA validation pipeline unchanged.

**Tech Stack:** Android Gradle, WorkManager, Kotlin, Compose, Gradle release signing.

---

### Task 1: Make manual OTA refresh always run

**Files:**
- Modify: `app/src/main/kotlin/com/smsguard/update/RuleUpdateScheduler.kt`

**Step 1: Confirm the failing behavior**

Manual checks use `ExistingWorkPolicy.KEEP`, which can leave the old work in place and prevent a fresh refresh.

**Step 2: Apply the minimal fix**

Switch the unique one-time work policy to `ExistingWorkPolicy.REPLACE`.

**Step 3: Verify**

Run `./gradlew testDebugUnitTest assembleDebug bundleRelease`.

### Task 2: Bump release version

**Files:**
- Modify: `app/build.gradle`

**Step 1: Update version metadata**

Set `versionCode` to the next integer and `versionName` to `0.1.5-alpha`.

**Step 2: Verify**

Re-run `./gradlew bundleRelease` and confirm the signed AAB is produced.

### Task 3: Package release artifacts

**Files:**
- Modify: none beyond Tasks 1-2

**Step 1: Inspect the output**

Confirm the bundle exists at `app/build/outputs/bundle/release/app-release.aab`.

**Step 2: Publish**

Commit the release branch, push it, and open a PR for review/merge.
